# Nota MVP 技术方案

> 对应《需求文档》。目标：最小成本跑通「说话/打字 → 摘要 + 待办 → 把事办了」闭环，同时把「每日 10 次额度在真实环境下准确」做成可证明的硬指标。

## 1. 总体架构

```
┌─────────────┐   HTTP/SSE    ┌──────────────────────────────┐
│  网页前端    │ ────────────▶ │  Node.js 后端 (Express)       │
│  纯 HTML/JS  │ ◀──────────── │  ├─ /api/chat  Agent 入口     │
│  (单页)      │   SSE 流式     │  ├─ Agent Loop (工具调用循环) │
└─────────────┘               │  ├─ Tools: 待办/提醒/历史      │
                              │  ├─ Quota 限额中间件           │
                              │  └─ Scheduler 定时提醒         │
                              └──────┬───────────────────────┘
                                     │ SQLite (better-sqlite3)
                                     │  users / todos / reminders /
                                     │  usage_log / messages / events
                                     ▼
                              ┌──────────────┐      ┌──────────────┐
                              │ DeepSeek API │      │ ESP32(加分项) │
                              │ (function    │      │ MQTT/HTTP 蜂鸣│
                              │  calling)    │      └──────────────┘
                              └──────────────┘
```

## 2. 技术选型与理由

| 项 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Node.js 20+ / Express | 题目允许；与前端同语言；SSE 原生友好 |
| 数据库 | SQLite（better-sqlite3，同步 API） | 零部署依赖，事务原子，单文件即可证明额度准确性；预留切换 PG 的 DAO 层 |
| 模型 | DeepSeek `deepseek-chat` | 国内模型、免费额度、原生支持 function calling（OpenAI 兼容协议）；仅依赖一个 SDK-less 的 HTTP 调用，换 Kimi/GLM 只改 base_url |
| Agent | 自研 ReAct 式工具循环（约 100 行） | 不引重框架，工具调用过程天然可序列化 → 直接喂给前端 SSE 做可视化（加分项） |
| 前端 | 纯 HTML + 原生 JS 单页 | MVP 最小；无构建步骤 |
| 提醒 | node-cron 轮询 reminders 表 + SSE 推送 | 服务端触发，重启后仍会补发过期提醒 |

## 3. Agent 设计

### 3.1 系统提示词（职责）
1. 从用户输入提取**摘要**（summary）与**待办**（todos）；
2. 自主决定调用工具把事办了（创建待办、设提醒等）；
3. 无法确定时先追问，不瞎造参数。

### 3.2 工具集（≥2，实际 5 个）

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `create_todo` | title, due?(ISO), priority? | 创建待办 |
| `set_reminder` | todo_id, remind_at | 给待办设提醒，Scheduler 到点经 SSE 推送 |
| `list_todos` | status?, keyword? | 查询待办 |
| `complete_todo` | todo_id | 标记完成 |
| `query_history` | keyword?(多词AND), since?, until?, days?, limit? | 检索历史记录：相对时间由 Agent 换算成时间范围；facts 优先命中，原文按时间倒序兜底 |
| `save_fact` | topic, content, person?, amount?, occurred_at? | 写入时结构化：把报价/金额/承诺等关键事实沉淀为可精确回忆的记录 |

### 3.3 工具调用循环
```
user input → LLM(带 tools) →
  ├─ 返回 tool_calls → 执行工具 → 结果回填 → 再次调 LLM（最多 N=6 轮）
  └─ 返回最终文本 → 组装 {summary, todos, steps} 返回前端
```
每一步（thought / tool_call / tool_result）实时写入 SSE，前端以时间线展示——同时满足「调用过程可见」加分项。

## 4. Free 每日 10 次额度：设计 + 证明（核心难点）

### 4.1 威胁模型（"真实使用环境下依然准确"指什么）
| 攻击/场景 | 对策 |
| --- | --- |
| 刷新页面 / 清 localStorage | 身份由服务端签发：`httpOnly cookie` 存 `uid`（匿名账号，首次访问注册），清 localStorage 不影响 |
| 清 cookie 换新身份 | 记录注册时的设备指纹（UA + 屏幕 + 时区哈希）与 IP；同指纹+IP 复用当日已注册的 uid 计数 |
| 重启服务丢计数 | 计数持久化在 SQLite `usage_log`（只追加），当日额度 = `count(usage_log where uid and day)`，非内存计数器 |
| 并发请求打穿（同时发 11 个） | 扣减用单条事务：`BEGIN IMMEDIATE` + 计数 + 插入，SQLite 写锁天然串行化，超 10 即拒绝 |
| 跨天边界 | 按用户本地时区折算的自然日（存 UTC，查询时转 Asia/Shanghai 当日 0 点窗口），并有单测覆盖 23:59:59 边界 |
| 多设备 | 诚实取舍：匿名产品无法绝对防多设备薅（除非手机号），方案中明确写进 README 取舍 |

### 4.2 计数口径
- 1 次「额度」= 1 次成功发起的 Agent 会话（`/api/chat`）；工具内部多轮调用、SSE 重连、查询类接口不计数。

### 4.3 证明方式（对应题目"自己想办法证明"）
`scripts/eval-quota.mjs` 自动化评测，输出报告 `data/eval-quota.json`：
1. 新用户连发 10 次成功、第 11 次 429 ✅
2. 清 localStorage（新 session）→ 因指纹/IP 仍命中同 uid，第 11 次仍 429 ✅
3. 并发 15 个请求同时打 → 恰好成功 10 个 ✅
4. 重启服务后再发 → 仍 429 ✅
5. mock 时间到次日 0 点 → 恢复 10 次 ✅
6. 超额响应体返回 `resetAt`（次日 0 点）与友好文案 ✅

另加 4.1 中跨天边界的单元测试。

## 5. 交互与 API

| 接口 | 说明 |
| --- | --- |
| `POST /api/chat` | 发起会话，返回 SSE：`step`（Agent 过程）→ `result`（summary+todos） |
| `GET /api/todos` | 待办列表 |
| `POST /api/todos/:id/complete` | 手动完成 |
| `GET /api/quota` | 当前剩余次数 |
| `GET /api/events` | SSE：提醒推送 |

前端：左侧对话区（含 Agent 步骤时间线 + 超额状态条），右侧待办看板（可勾选完成），顶部剩余额度。

## 7. 里程碑

1. **M1 骨架**：Express + SQLite + 静态页，`/api/chat` 直通 DeepSeek，返回摘要+待办。
2. **M2 Agent**：工具循环 + 5 个工具 + SSE 步骤流；待办看板联动。
3. **M3 额度**：匿名账号/指纹 + 事务计数 + eval-quota 全绿。
4. **M4 提醒**：Scheduler + SSE 到点推送，重启补发。
5. **M5 加分项**（按性价比排序）：README 架构图与三者关系图 → 历史问答（query_history 已具备）→ 效果评测样例集 → ESP32 提醒蜂鸣（Wokwi 仿真即可打通）→ App 版本。

## 8. 关键取舍（README 用）

- 自研 100 行 Agent 循环替代框架：换取工具调用全程可序列化、可直接做界面可视化。
- SQLite 替代 PG/Redis：MVP 单机即可让额度计数具备事务性与持久性，证明成本最低；DAO 隔离保留升级路径。
- 匿名 cookie 身份 + 指纹兜底：不引入注册登录的前提下，把"刷新/清缓存重置计数"挡住；多设备薅羊毛是已知取舍，写明即可。

## 9. 长记忆：答对"我上个月跟张总聊的那个报价是多少？"

用户用半年后积累上千条记录，问回忆类问题。三层机制（实现 + 可证明）：

1. **写入时结构化（save_fact，加速层）**：对话中出现报价、金额、承诺等关键事实时，Agent 顺手沉淀 `(人名, 主题, 数值, 时间)` 到 facts 表——回忆类问题优先命中结构化事实，不靠翻原文碰运气。
   - **定位**：facts 是加速/精确层，不是唯一路径。原文（messages）才是真相源，`query_history` 永远同时查两层，save_fact 漏存不会导致答错（评测 H5/H6 专门验证这一点）。
   - **抗漏写（backfill）**：`npm run backfill` 对未提炼过的历史消息批量跑 LLM 提取（幂等：`facts.src_id` / `backfill_done` 双重去重，失败批次不标记可重试），夜间定时跑即可让 facts 层收敛，不依赖模型当场"记得"。
   - **防滥用**：提示词约束只对"本次对话新出现"的关键事实调用，检索到的旧记录不重复保存，日常琐碎不存；字段设计上 content 全文参与匹配，枚举字段不限制可回答的问题类型。
2. **查询时检索管道（query_history）**：
   - 相对时间归一：提示词注入当前时间，"上个月/上周"必须先换算成 since/until（ISO）；
   - 多关键词 AND："张总 报价"同时匹配，人名消歧（库里还有李总报价 8.8 万、张总旧报价 9.6 万干扰）；
   - facts 优先 + 原文全文检索兜底，按时间倒序、超长截断；
   - 一次查不到可放宽条件再试（提示词允许最多再试 2 次）。
3. **回答时强接地**：只准引用工具返回的原文给结论与时间；查不到坦诚说明并给最接近候选，禁止编造。

规模说明：上千条记录下 JS 侧 AND 过滤毫秒级完成；若到十万条级，升级路径是 SQLite FTS5（trigram 分词支持中文）→ PG 全文 → 向量库，接口不变。

验证：`npm run seed:history`（半年 1300+ 条 + 目标记录 + 干扰项）+ `npm run eval:history`（H1 时间+关键词精确命中 12.8 万且排除旧报价、H2 短词召回、H3 证明时间换算必要性、H4 端到端真实提问、H5 清空 facts 后纯原文检索仍命中、H6 facts 缺失时端到端仍答对）+ `npm run backfill`（事实兜底提炼演示）。

## 10. 记忆系统：现状与演进路线

当前实现已构成记忆系统的骨架，按认知科学分层对应：

| 层 | 实现 | 说明 |
| --- | --- | --- |
| 工作记忆 | Agent 循环内最近 12 条上下文 | system prompt + 近期对话 |
| 情景记忆（episodic） | `messages` 原始流水 | 对话/录音转写全文，永久持久化，检索式取用（不塞 context） |
| 语义记忆（semantic） | `facts` 结构化事实 + backfill 收敛 | 人/事/数值/时间，可精确命中 |
| 任务记忆 | `todos` | 待办与提醒 |
| 检索层 | 时间归一 + 多关键词 AND + facts/原文双层查询 | 毫秒级（千条规模） |

**何时才升级为完整记忆系统（触发条件）**：记录达数万条且关键词命中率下降 → 加向量层；出现"我是什么样的人/我的偏好"类画像问题 → 加蒸馏（consolidation）；事实会过时且影响决策 → 加 latest-wins；需要主动记忆 → 加画像表。当前规模均未触发，引入 mem0 类黑盒依赖属过度设计。

**增量路线（不动现有表结构）**：
1. 夜间蒸馏：定时把当日 messages 蒸馏为"日摘要"表 + 维护用户画像表（常联系人/偏好/未了事项）——即 write→extract→consolidate→retrieve 的核心循环，新增两张表；
2. 向量兜底：关键词 miss 时启用 embedding 余弦相似度（千条规模可直接 JS 计算，无需向量库）；
3. 事实时效：facts 加 `superseded_by`，查询 latest-wins，替代当前靠提示词的软消歧。
